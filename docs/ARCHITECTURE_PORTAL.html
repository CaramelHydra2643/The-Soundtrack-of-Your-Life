Architecture at a glance

The implementation is a modular monolith. Python modules collaborate in-process; FastAPI is the REST boundary.

RAG and semantic retrieval

Knowledge RAG

music_knowledge stores conceptual emotion, genre, instrument, context, and cultural documents. It informs context and ranking; it does not directly generate tracks.

Track retrieval

music_tracks stores embeddings of real track metadata profiles and returns candidate IDs. It is separate from knowledge retrieval.

Fusion

SoundtrackService builds emotional, musical, and contextual queries. RAGEngine normalizes distances, adds rank contribution, deduplicates, and bounds results.

Persistence

MemoryVault SQLite

memories, feedback, and preferences are created by modules/memory_vault.py. Track recommendations are stored as JSON snapshots.

CatalogueStore

Separate SQLite metadata index used for source, language, genre, region, availability, and release-year filtering.

ChromaDB

Two collections: music_knowledge and music_tracks.

Security and privacy

Local processing

Ollama, embeddings, RAG, ranking, SQLite, and ChromaDB run locally. Browser speech can use the browser provider.

Secrets

Spotify credentials remain in ignored .env and never enter React code.

Audio

faster-whisper validates uploads, uses a temporary file, transcribes, then removes it.

Performance and fallbacks

  • Expensive services are cached per API process.
  • Track embeddings are precomputed; requests do not embed the catalogue.
  • Deterministic explanations avoid a second Ollama call by default.
  • Unavailable Chroma falls back to catalogue scoring.
  • Provider failures preserve recommendations without fabricated metadata.
  • Full track indexing is a resumable CPU batch.

Limitations

Open catalogues do not guarantee commercial-provider matches, previews, or complete regional language coverage. Full semantic indexing is CPU-intensive. Optional external services may fail without blocking core recommendations.
